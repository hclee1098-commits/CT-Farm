# LOCAL부터 운영 배포와 통합 모니터링까지 실행 안내

> **알 수 있는 것:** LOCAL → STAGING → PRODUCTION 구성, 안전한 배포, 환경별 로그 조회와 장애 대응
>
> **읽을 때:** 이 버전을 처음 실행하거나 서버에 배포할 때
>
> **관련 소스:** [생명주기](../../SECURE-LIFECYCLE.ps1), [수집기](../../tools/monitoring/collector.mjs), [서버 배포](../../tools/deployment/release.mjs), [CI/CD](../../.github/workflows/promote.yml)
>
> **관련 문서:** [문서센터](../README.md), [이번 검증 결과](../07-기술참고/환경별-모니터링-검증결과.md)

이 문서는 이번 변경의 실행 기준입니다. 과거 검증 보고서는 당시 결과이며 현재의 원격 배포 성공 증거가 아닙니다. Windows·Docker·실제 원격 서버는 이번 실행 환경에 없어 직접 검증하지 못했습니다. 서버 구축 부분은 관리자가 실제 주소·인증서·인증키를 채운 후 검증해야 합니다.

## 1. SECURE STARTER V6 시작하기

기존 docs-center 프로젝트를 수정한 버전입니다. EXE를 만들지 않았습니다. 관리 명령은 `SECURE-LIFECYCLE.ps1 -Action SETUP|STARTER|STOP`입니다. 압축은 별도 폴더에 풀어 변경을 확인하고, 기존 프로젝트에 적용하기 전 전체 폴더와 DB·업로드를 백업하세요. 기존 `.env`, `.starter-state/identity.json`, Docker 볼륨, 업로드, 마이그레이션 이력을 새 프로젝트 파일로 덮어쓰면 안 됩니다. 기존 실행 프로세스는 기존 스크립트의 STOP으로 종료한 후 적용합니다.

| 구분 | LOCAL | STAGING | PRODUCTION |
|---|---|---|---|
| 실행 | Windows Node API/WEB + 로컬 DB/Redis | 독립 Linux Docker 서버 | 별도 Linux Docker 서버 |
| 환경 식별 | LOCAL | STAGING | PRODUCTION |
| Node 런타임 | development | production | production |
| Compose | 기존 compose.yaml | compose.server.yaml + 별도 env | compose.server.yaml + 별도 env |
| 데이터 | 기존 프로젝트 전용 볼륨 유지 | 앱ID-staging 전용 볼륨 | 앱ID-production 전용 볼륨 |
| 관리 권한 | 로컬 프로세스만 | STAGING 배포 계정 | 승인된 운영 배포 계정 |

`NODE_ENV=production`만으로 운영 환경을 식별하지 않습니다. STAGING도 운영 빌드로 실행하므로 `APP_ENV`를 별도로 검증합니다.

## 2. LOCAL 개발 환경 설치

Windows PowerShell 5.1, Node.js 22 이상, 실행 중인 Docker Desktop이 필요합니다. 프로젝트 루트에서 실행합니다.

```powershell
# 필수 프로그램 확인
node --version
docker info

# 기존 환경과 데이터는 유지하면서 설치 절차 실행
.\SECURE-LIFECYCLE.ps1 -Action SETUP
if ($LASTEXITCODE -ne 0) { throw '설치 실패: 위 오류를 먼저 해결하세요.' }
```

원본 SETUP의 프로젝트 ID·Docker 소유권 확인·환경설정 생성·연결 확인을 유지했습니다. 기존 설치에서 SETUP이 위험하다고 판단하여 중단하면 우회하지 말고 출력과 백업을 확인하세요. 기존 .env를 지우거나 DB를 초기화하지 마세요.

## 3. STAGING 서버 구축

별도의 Linux 서버에 Node.js 22 이상과 Docker Engine/Compose 플러그인을 준비합니다. 외부 포트는 서비스 HTTPS 및 허용된 배포 접속만 사용합니다. DB와 Redis에는 호스트 ports를 만들지 않습니다.

서버 관리자가 수정 소스를 `/srv/secure-starter/app`에 배치합니다. 기존 서버를 전환할 때는 현재 볼륨을 새 이름으로 임의로 바꾸지 말고 별도의 전환·복원 검증을 진행하세요. 새 compose.server.yaml은 기존 compose.production.yaml의 볼륨을 자동 인계하지 않습니다.

```bash
# 아래 경로와 계정은 서버 관리자가 준비합니다.
cd /srv/secure-starter/app
umask 077
mkdir -p .starter-state/monitoring
# 컨테이너 node 사용자와 배포 계정이 이 경로를 읽고 쓸 수 있어야 합니다.
# 별도 그룹을 사용할 때는 배포 계정의 UID/GID 정책에 맞게 조정합니다.
sudo chown -R 1000:1000 .starter-state/monitoring
chmod 700 .starter-state/monitoring
sudo mkdir -p /etc/secure-starter /run/secrets
sudo cp deploy/staging.env.example /etc/secure-starter/server.env
sudo chmod 600 /etc/secure-starter/server.env
```

`server.env`는 배포 전용 계정이 읽을 수 있게 소유권을 설정합니다. `APP_ENV=STAGING`, `DEPLOY_ENV=staging`, `APP_ID=secure-myapp`, `POSTGRES_DB=secure_myapp_staging`을 함께 설정합니다. `DATABASE_URL`은 **컨테이너 내부 postgres**와 해당 DB를 가리켜야 합니다. URL의 비밀번호는 POSTGRES_PASSWORD와 같아야 합니다. 예시 문자열이 들어 있는 키는 배포 검증에서 거부됩니다.

## 4. PRODUCTION 서버 구축

STAGING과 다른 서버·계정·볼륨·DB 이름·키·도메인을 사용합니다. `deploy/production.env.example`을 운영 서버의 `/etc/secure-starter/server.env`로 복사하고 운영 값만 설정합니다. STAGING의 데이터나 비밀키를 그대로 복사하지 마세요. 운영 서버에 STAGING 개인 서명키 또는 운영 승인 개인키를 두지 않습니다.

최초 설치에도 배포 스크립트는 DB/Redis 준비 → 암호화 DB/업로드 백업 → 선택적 migration deploy → 이미지 시작 → HTTPS 헬스체크를 수행합니다. 최초 DB에 스키마가 없으면 검토한 명세의 `backwardCompatible: true`와 서버의 `DEPLOY_MIGRATE=1`이 필요합니다. 마이그레이션 코드와 기존 DB 백업 검토 없이 1로 바꾸지 마세요.

DNS와 SITE_DOMAIN을 일치시키고 Caddy가 80/443에 접근해 인증서를 발급받을 수 있어야 합니다. 실제 인증서 발급과 Docker 실행은 외부 설정 필요 항목입니다.

## 5. 환경별 설정과 키 관리

서버 설정 파일은 Git에 넣지 않습니다. 이미지는 digest로 고정하고 실행 환경 값은 주입합니다. WEB의 CI 빌드는 `NEXT_PUBLIC_API_BASE_URL=same-origin`을 사용하므로 STAGING에서 검증한 WEB 이미지를 도메인이 다른 운영에 재빌드 없이 사용합니다. 기존 LOCAL의 localhost API 설정은 유지됩니다.

| 키 | 두는 곳 | 권한 |
|---|---|---|
| 각 환경 MONITOR_WRITE_TOKEN | 해당 환경 collector | 자기 환경 이벤트 전송만 |
| STAGING/PRODUCTION READ_TOKEN | 허가된 로컬 포털 프로세스 | 자기 환경 조회만 |
| hub의 6개 토큰 | 중앙 수집 서버 | 각 환경 읽기/쓰기 매핑 |
| STAGING 영수증 개인키 | STAGING 배포 서버 | 검증 영수증 서명 |
| STAGING 영수증 공개키 | 운영 서버 | 검증 영수증 확인 |
| 운영 승인 개인키 | GitHub production 환경 secret 또는 별도 승인자 | 동일 명세 승인 서명 |
| 운영 승인 공개키 | 운영 서버 | 승인 확인 |

토큰 6개는 모두 다르게 생성해야 합니다. hub는 중복 키와 짧은 키로 시작하지 않습니다. 키 생성 예:

```bash
node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
# STAGING에서만 영수증 서명용 키 생성
openssl genpkey -algorithm ED25519 -out /run/secrets/staging-receipt.key
openssl pkey -in /run/secrets/staging-receipt.key -pubout -out /run/secrets/staging-receipt.pub
# 별도 승인자 환경에서 운영 승인 키를 생성하고 공개키만 운영에 전달
openssl genpkey -algorithm ED25519 -out production-approval.key
openssl pkey -in production-approval.key -pubout -out production-approval.pub
```

각 DB 비밀번호·JWT·MFA·백업·모니터링 키는 독립 생성합니다. JWT issuer/audience도 환경별로 분리하여 다른 환경에서 토큰을 수용하지 않습니다. LOCAL의 기존 형식은 유지하고 원격 환경을 새로 적용할 때는 재로그인이 필요합니다. MFA와 BACKUP_KEY는 64자리 HEX입니다. 기존 사용자의 MFA/백업 키는 임의로 교체하면 기존 데이터 복호화가 불가능하므로 신규 서버 키 생성과 기존 서버 키 회전을 구분하세요. 키 회전 시 새 읽기/쓰기 쌍을 안전하게 배포하고 수집 재개를 확인합니다.

## 6. SECURE-LIFECYCLE.ps1 사용법

```powershell
# 현재 프로젝트의 DB/Redis 확인 후 API, WEB, LOCAL 수집기 시작
.\SECURE-LIFECYCLE.ps1 -Action STARTER

# 현재 프로젝트 실행 기록·시작 시각·실행 파일·명령을 검증한 프로세스만 종료
.\SECURE-LIFECYCLE.ps1 -Action STOP
```

STARTER는 `APP_ENV`가 STAGING/PRODUCTION이면 거부합니다. 수집기는 프로젝트 고정 경로와 고정 포트 인자를 가진 Node 프로세스로 실행하고 runtime.json에 별도로 기록합니다. STOP은 해당 기록을 검증해 수집기·WEB·API를 정리합니다. 강제 종료 시 마지막 종료 이벤트가 디스크에 남지 않을 수 있으므로 heartbeat 만료와 HTTP 상태 점검으로 보완합니다. 포털은 별도 터미널에서 실행하며 STOP이 임의의 포털이나 다른 프로젝트 프로세스를 종료하지 않습니다.

이전 버전으로 실행한 서버가 이미 살아 있으면 새 수집기가 없다는 안내가 표시될 수 있습니다. 이전 버전의 STOP으로 먼저 종료한 뒤 새 STARTER로 시작하세요. runtime.json을 임의 삭제하여 소유권 검사를 우회하지 마세요.

## 7. Docker 사용법

LOCAL은 기존 compose.yaml과 생성된 COMPOSE_PROJECT_NAME을 유지합니다. 원격은 `APP_ID-DEPLOY_ENV` 프로젝트 이름으로 DB·Redis·업로드 볼륨을 분리합니다. backend 네트워크는 internal이고 DB/Redis 호스트 관리 포트는 없습니다. API·WEB·collector에는 상태 확인과 재시작 정책을 적용했습니다. Docker 원문 로그도 10MiB × 3개로 제한했습니다.

```bash
# 설정과 승인 검증을 수행하는 배포 진입점을 통해 시작하세요.
# 상태 조회는 데이터를 변경하지 않습니다.
docker compose --env-file /etc/secure-starter/server.env -f compose.server.yaml ps
```

이미지 변수(API_IMAGE 등)는 배포 프로그램이 명세에서 process 환경에 주입하므로 일반 터미널에서 Compose를 조회하려면 current.json의 digest 값을 같은 셸에 먼저 로드해야 합니다. 비밀정보가 출력될 수 있는 전체 `compose config` 출력은 공유하지 마세요. 배포 스크립트는 `config --quiet`만 호출합니다. 기존 볼륨 삭제·초기화 명령은 이 절차에서 사용하지 않습니다.

## 8. 개발 서버 배포

GitHub 저장소 관리자가 `.github/workflows/promote.yml`을 검토하고 활성화합니다. 이번 작업에서는 커밋·push·실제 배포를 하지 않았습니다. main의 검증된 변경 또는 workflow_dispatch로 검증 → 이미지 4종(API/WEB/migrate/collector) 빌드 → GHCR digest 명세 저장 → STAGING 배포가 이어집니다.

STAGING/PRODUCTION에는 각각 전용·가급적 일회용 self-hosted runner를 배치합니다. 공개 PR과 배포 runner를 공유하지 마세요. runner에는 GHCR 읽기 권한과 해당 서버 Docker 권한만 부여합니다. Docker 권한은 서버 변경 권한이므로 모니터링 조회 사용자에게 주지 않습니다.

서버 관리자가 `deploy/deploy-reviewed-release.sh`를 `/srv/secure-starter/bin/deploy-reviewed-release`에 설치하고 실행 권한을 부여합니다. 이 고정 진입점은 저장소의 .env 대신 `/etc/secure-starter/server.env`만 읽고 서버용 배포 코드를 호출합니다. 현재 소스는 `/srv/secure-starter/app`에 배치해야 합니다. runner 라벨은 `secure-staging`, `secure-production`을 구분합니다.

배포 후 실제 HTTPS readiness, WEB 상태 경로, 미인증 사용자 차단을 통과하면 STAGING이 명세 hash에 대한 Ed25519 영수증을 발급합니다. 이는 스모크 검증 증거이며 실제 업무 데이터에 대한 전체 인수 테스트를 대체하지 않습니다. 조직의 통합·보안 테스트를 STAGING job에 추가하세요.

## 9. 운영 서버 배포와 승인

GitHub Settings → Environments → production에서 Required reviewers, 자기 승인 금지, 허용 브랜치 제한을 설정합니다. 요금제/저장소 공개 범위에 따라 기능 제공이 다를 수 있습니다. 지원되지 않으면 별도 승인자가 오프라인 서명한 명세만 사용하고 자동 서명 job을 활성화하지 마세요.

production 환경 secret `PRODUCTION_APPROVAL_PRIVATE_KEY`에 승인 개인키 PEM을 저장합니다. 승인 전에는 이 secret에 접근할 수 없도록 환경 보호 규칙을 반드시 설정해야 합니다. YAML만 저장한다고 GitHub 승인 설정이 자동 생성되는 것은 아닙니다. 참고: https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments

운영 배포는 STAGING 영수증과 운영 승인 서명을 **같은 release.json의 hash**로 확인합니다. 영수증·승인은 24시간 후 만료하며 이미지 tag가 아닌 digest만 허용합니다. 승인 후 임의로 명세를 고치면 실패합니다. 승인 키 누락·영수증 누락·서명 불일치는 배포를 중단합니다.

## 10. 환경별 로그 확인과 수집 서버 구축

환경마다 API는 api-runtime.jsonl, WEB은 web-http.jsonl, 수집기는 서비스별 jsonl에 기록합니다. 저장 경로는 `.starter-state/monitoring/<APP_ENV>/`입니다. 원문 URL, 헤더, 본문, JWT, 쿠키, 이메일 주소, 사용자 이름·ID는 모니터링 이벤트에 넣지 않습니다. 자유 텍스트 메시지를 수집하지 않고 허용된 숫자·상태·UUID·버전만 유지합니다.

중앙 hub는 독립된 관리 서버에서 실행합니다. `deploy/monitoring.env.example`의 여섯 토큰과 유효한 인증서·개인키를 별도 환경 파일로 설정합니다. `npm run monitor:hub`는 직접 HTTPS만 허용합니다. 기본 bind는 127.0.0.1이므로 원격 전송을 받으려면 방화벽/IP 제한을 설정하고 MONITOR_BIND를 해당 관리 인터페이스로 명시하세요. TLS 검증을 끄는 설정은 제공하지 않습니다. 내부 CA는 신뢰 저장소 또는 NODE_EXTRA_CA_CERTS로 등록합니다.

파일로 설정을 준비했다면 다음처럼 명시적으로 불러옵니다. `npm run monitor:hub`는 이미 셸에 주입된 환경변수를 사용하며 env 파일을 자동으로 읽지 않습니다.

```bash
node --env-file=/etc/secure-monitor/hub.env tools/monitoring/hub.mjs
```

[systemd 서비스 예제](../../deploy/monitor-hub.service)를 제공합니다. `secure-monitor` 계정, `/srv/secure-monitor/data` 소유권, `/etc/secure-monitor/hub.env` 읽기 권한, 인증서 경로와 실제 Node 실행 파일을 먼저 설정하세요. hub를 systemd 등 독립 서비스 관리자로 실행해 장애 후 재시작되게 하세요. API 컨테이너나 개발자 포털에 hub를 합쳐 실행하지 않습니다. collector는 10초마다 로컬 파일을 읽고 자기 환경 WRITE_TOKEN으로 `/v1/events`에 전송합니다. 실패 시 파일을 유지하고 재시도하며 ID로 중복 제거합니다. 최근 heartbeat/health를 우선 전송해 요청 로그 적체가 현재 상태 표시를 막지 않게 합니다.

저장/조회 보관 범위는 7일, 파일 상한은 약 8MiB, 집계에 읽는 최대 이벤트는 10000건입니다. API/WEB 큐는 500건을 넘으면 관측 이벤트를 버리고 서비스 요청을 계속 처리합니다. 파일 상한 도달 시 회전·삭제가 있으므로 장애 없는 영구 감사 저장소나 손실 없는 과금 지표로 사용하면 안 됩니다. 원문 실행 로그는 별도 민감 자료로 접근을 제한하세요.

## 11. 통합 운영 모니터링 사용법

프로젝트 루트의 별도 PowerShell에서 실행합니다.

```powershell
# 로컬 포털 전용 임시 접근키 생성 (일반 사용자 JWT와 별개)
$env:DEV_PORTAL_TOKEN = & node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
# 화면에서 입력할 접근키를 본인 PC에서 확인
$env:DEV_PORTAL_TOKEN
npm run dev:portal
```

http://127.0.0.1:4310/ 에서 키를 입력하고 **운영 모니터링** 또는 **실시간 로그**를 엽니다. 키는 1시간 유효하며 영구 저장하지 않습니다. 포털을 인터넷에 공개하지 마세요.

원격 조회를 쓰려면 포털을 시작하는 셸에 다음 환경변수를 보안 경로로 주입합니다. 두 URL은 같은 hub일 수 있지만 READ_TOKEN은 반드시 다릅니다.

```text
MONITOR_STAGING_URL=https://monitor.example.com:9443
MONITOR_STAGING_READ_TOKEN=<STAGING 읽기 전용 키>
MONITOR_PRODUCTION_URL=https://monitor.example.com:9443
MONITOR_PRODUCTION_READ_TOKEN=<PRODUCTION 읽기 전용 키>
```

화면 상단에서 환경을 선택합니다. 전체 환경에서는 세 환경 카드가 함께 표시됩니다. 서비스·수준·15분/1시간/24시간·검색 조건을 조합할 수 있습니다. SSE는 약 5초마다 갱신하고 끊기면 재시도합니다. 필터 변경과 메뉴 이탈 때 이전 연결을 닫습니다. 조회 키 만료 시 포털 재시작 및 새 접근키가 필요합니다.

- `수집되지 않음`: 관측 근거가 아직 없습니다. 요청 0건과 다릅니다.
- `연결됨`: 최근 collector heartbeat가 있습니다. API 정상이라는 뜻은 아닙니다.
- `수집 중단 감지`: heartbeat가 45초 넘게 갱신되지 않았습니다.
- `관측 만료`: 서비스의 마지막 상태 확인이 오래되어 정상으로 확정할 수 없습니다.
- API 상태는 DB/Redis를 포함한 readiness입니다. API가 내려가면 DB/Redis를 독립 접속하여 추측하지 않고 미확인으로 표시합니다.
- 이메일/백업은 최근 실제 발송/실행 결과입니다. 24시간이 지나면 미확인입니다. 지속적인 SMTP 연결 건강 상태나 예약 백업 스케줄러를 뜻하지 않습니다.
- HTTP 오류는 4xx와 5xx입니다. 오류율은 관측된 API 요청 중 비율이며 요청이 없으면 계산하지 않습니다.
- 배포 기록이 없으면 이력을 만들어 넣지 않습니다. 로그의 version과 배포 이력의 version으로 관련 장애를 추적합니다.

## 12. 백업 및 복원

기존 tools/backup.mjs의 인증된 암호화 백업과 격리 복원 기능을 유지했습니다. 생성 성공/실패를 모니터링에도 기록합니다. 배포 프로그램은 API/WEB 쓰기를 멈춘 후 pg_dump와 업로드 tar를 별도 AES-256-GCM 파일로 백업합니다. 실패 시 마이그레이션을 시작하지 않습니다. 외부 작업자도 DB/파일을 수정한다면 관리자가 먼저 중지해야 일관성이 확보됩니다. 이번 프로젝트에는 외부 작업자 제어 기능을 추가하지 않았습니다.

배포 백업 포맷은 `SSV6DEP1(8바이트) + IV(12바이트) + 암호문 + 인증태그(16바이트)`이며 기존 `.ssbk`와 별개입니다. 새 [백업 해제 도구](../../tools/deployment/decrypt-backup.mjs)는 인증 확인 후 새 파일로만 해제하며 DB를 변경하지 않습니다. 해제된 database.dump는 새 격리 DB에 pg_restore로 검증하고, uploads.tar.gz도 새 디렉터리에 검사하여 복원합니다. 실제 운영 DB를 자동으로 되감지 않습니다. Redis는 이 배포에서 기존 AOF 볼륨을 유지하며 별도 Redis 백업 정책은 서버 관리자가 설정해야 합니다.

## 13. 장애 대응

환경 선택 → 마지막 수집 시간 → 수집기 연결 → API/WEB/DB/Redis 상태 → 오류 수준 필터 → 배포 version 순서로 확인합니다. 수집기 단절과 서비스 장애를 구분하세요. 원격 조회 실패라면 DNS·TLS 인증서·환경별 조회 키를 확인합니다. hub 키와 서버 변경 권한은 다릅니다. DB 관리 포트를 열어 해결하지 마세요.

고부하·디스크 부족으로 관측 이벤트가 누락될 수 있습니다. 지속적인 알림 전송(이메일/메신저/호출)은 구현 범위에 포함하지 않았으므로 운영 감시 시스템과 연결하려면 별도 설정이 필요합니다. 디스크/CPU/메모리 지표도 이 버전의 수집 대상이 아닙니다.

## 14. 롤백

배포 후 헬스체크 실패 시 이전에 성공한 current.json의 이미지 digest로 API/WEB/collector를 복구하고 HTTPS 상태를 다시 확인합니다. DB 마이그레이션은 되돌리지 않습니다. 이전 이미지와 새 스키마의 호환성은 배포 전에 검토해야 합니다. 실패한 최초 설치에는 이전 이미지가 없으므로 자동 복구할 대상이 없습니다.

수동 롤백은 서버에서 이전 release.json을 선택하고 새로운 유효한 승인/검증 증명을 준비한 뒤 `node tools/deployment/release.mjs rollback <이전-release.json>`을 실행합니다. 운영에서는 이전 버전이라도 승인 검증을 생략하지 않습니다. DB를 복원할 경우 쓰기 중지·격리 복원 시험·데이터 유실 범위 검토·별도 승인이 필요합니다. 재배포를 재시도하기 전 마이그레이션 적용 상태와 deploy.lock을 확인하세요. 잠금 파일은 실행 중인 배포가 없는 것을 확인한 관리자만 정리합니다.

## 15. 보안 관리와 검증

수집기는 자기 환경 쓰기만, 로컬 포털은 승인된 환경 읽기만 허용합니다. TLS 서버는 256KiB 요청·배치 200건·키별 분당 120회 제한을 적용합니다. 인증키·요청 원문을 오류 출력에 포함하지 않습니다. 서버 로그 디렉터리는 비공개 권한으로 운영합니다. 인증서·키·DB·실제 로그는 결과 ZIP에 포함하지 않습니다.

```powershell
# 코드·테스트 검증 (DB 초기화 명령 없음)
npm run check:source
npm run db:generate
npm test
npm run test:monitoring
npm run test:deployment
npm run predev:portal
npm run test:portal
npm run test:docs
npm run test:sql
npm run test:backup
npm run build
npm run test:web-observed
```

SQL 테스트는 PGlite 격리 실행이며 네이티브 PostgreSQL 검증을 대체하지 않습니다. Windows에서 PS1 문법과 실제 SETUP/STARTER/STOP, Docker 컨테이너, 네이티브 Redis, 원격 배포/롤백을 추가 검증해야 합니다. 각 범위는 최신 검증 보고서에 따로 표시했습니다.

## 16. 자주 발생하는 오류

| 증상 | 확인할 것 |
|---|---|
| LOCAL 로그 없음 | 기존 서버를 STOP 후 새 STARTER로 시작했는지, runtime.json의 collector와 collector-error.log |
| 포털 미실행 | 별도 터미널의 npm run dev:portal, 접근키와 127.0.0.1 주소 |
| 원격 설정 필요 | 포털 셸의 환경별 URL/READ_TOKEN |
| 원격 연결 실패 | 인증서 신뢰, DNS, 방화벽, 키의 읽기 권한·환경 매핑 |
| API 장애인데 DB 미확인 | API readiness에 접근할 수 없는 상태이며 DB 정상/장애를 확정하지 않음 |
| 메일 미설정/미확인 | SMTP 설정과 최근 실제 발송 여부, 24시간 관측 만료 |
| 로그 저장 권한 오류 | 호스트 `.starter-state/monitoring`이 UID 1000에게 쓰기 가능한지 |
| 배포 명세 거부 | 모든 이미지가 ghcr.io digest인지, version이 Git SHA인지 |
| 운영 승인 실패 | 동일 명세의 STAGING 영수증·운영 서명·공개키·24시간 유효기간 |
| 배포 이전 상태가 이미 장애 | 복구 배포가 필요한 경우 관리자 검토 후 DEPLOY_ALLOW_UNHEALTHY=1을 한시 적용 |
| 설치 후 빈 DB | 신규 설치의 migration deploy 검토 및 DEPLOY_MIGRATE 설정 확인 |
| 롤백 후 오류 계속 | DB 스키마 호환성, 데이터 상태, 외부 의존성 점검. DB 자동 되감기 없음 |

원격 환경의 실제 인증서·서버·GitHub 설정은 자동으로 만들어졌다고 가정하지 마세요. 남은 설정은 [남은 작업](../07-기술참고/환경별-모니터링-남은작업.md)을 확인하세요.
