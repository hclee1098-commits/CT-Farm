# 실제 서버 적용 전 남은 설정과 미검증 항목

이번 작업은 기존 소스를 수정하고 Linux 격리 테스트를 실행했습니다. 실제 Windows PC, Docker 엔진, STAGING/PRODUCTION 서버, GitHub 저장소 권한은 연결되지 않았습니다. 다음 작업이 남아 있으므로 전체 운영 배포 완료로 판단하면 안 됩니다.

| 구분 | 상태 | 관리자 작업과 완료 증거 |
|---|---|---|
| Windows PowerShell 5.1 | 미검증 | 파서 검사, SETUP/STARTER/STOP, 공백·한글 경로, 프로젝트 2개 동시 실행·종료, 수집기 소유권 확인 |
| LOCAL Docker Desktop | 미검증 | 기존 볼륨을 유지한 DB/Redis 실행, 실제 연결과 기존 데이터 비교 |
| 네이티브 PostgreSQL/Redis | 미검증 | Prisma·실제 Redis·HTTP 통합 테스트, pg_dump/pg_restore 격리 복원 |
| STAGING 서버 | 외부 설정 필요 | 독립 호스트, 계정, 도메인, 키, GHCR 읽기 권한, 볼륨 권한 설정 후 실제 Compose 실행 |
| PRODUCTION 서버 | 외부 설정 필요 | 운영 호스트와 별도 키/볼륨/권한, 승인 공개키, HTTPS 헬스체크 |
| 중앙 수집 서버 | 외부 설정 필요 | 별도 관리 호스트, TLS 인증서, 방화벽, 여섯 독립 토큰, 서비스 재시작 정책 |
| 원격 포털 연결 | 외부 설정 필요 | 환경별 읽기 URL/키를 로컬 포털에 주입하고 실제 전송·조회·단절 복구 확인 |
| GitHub 승인 | 외부 설정 필요 | production Required reviewers·자기 승인 금지·브랜치 제한·승인 키 secret 설정; 요금제 미지원 시 별도 승인자 서명 |
| Runner·자동 배포 | 외부 설정 필요 | 전용·가급적 일회용 runner 라벨과 고정 배포 진입점, 실제 STAGING→운영 같은 digest 확인 |
| 실제 애플리케이션 롤백 | 미검증 | Docker 실패 주입 후 이전 이미지 건강 상태 확인; 현재는 대체 Docker 실행기로 제어 흐름만 테스트 |
| 실제 DB/업로드 백업·복원 | 미검증 | 실제 pg_dump·tar 암호화 후 별도 DB/디렉터리에 복원해 데이터 비교 |
| SMTP 외부 발송 | 외부 설정 필요 | TLS SMTP 계정과 도달 확인. 격리 TCP SMTP만 이번에 테스트 |
| 화면 시각 QA | 미검증 | 실제 Chromium·Edge에서 작은 화면/넓은 화면·스크롤·키보드·SSE 재연결 확인. DOM 동작만 테스트 |

## 구현 범위와 운영 제한

- 이메일/백업 상태는 최근 실제 작업 결과이며 지속적인 SMTP 네트워크 검사나 백업 스케줄러는 아닙니다.
- API가 내려가면 readiness 경유 DB/Redis 상태는 미확인입니다. 관리 포트를 열어 추측하지 않습니다.
- 로컬 JSONL 저장·전송은 제한된 관측 데이터입니다. 부하·용량 상한에서 유실될 수 있고 감사 DB의 영구 보관을 대체하지 않습니다. API/WEB 큐는 500건, 서비스별 파일 약 8MiB, 조회 최대 10000건·7일입니다.
- 운영 경보의 외부 알림·CPU/메모리/디스크 지표·다중 collector/다중 hub 동시 쓰기·대규모 장기 로그 검색은 추가 구축 대상입니다. 이 버전은 환경당 단일 API/WEB writer 및 collector, 단일 hub writer 기준입니다.
- JWT·비밀번호·개인정보·원문 오류와 URL을 제거하므로 오류 상세 원문은 표시하지 않습니다. 요청 ID·HTTP 상태·버전·의존성 상태로 연관시킵니다.
- 운영 DB 스키마의 자동 역마이그레이션은 제공하지 않습니다. 자동 애플리케이션 롤백은 DB 변경이 하위 호환일 때만 유효합니다.
- 최초 배포에는 이전 이미지가 없으므로 실패 시 자동 복구 대상이 없습니다. 실패 상태와 백업을 확인한 뒤 수정 배포가 필요합니다.
- 강제 종료 순간 마지막 이벤트가 손실될 수 있습니다. heartbeat 만료와 HTTP 점검이 상태를 보완합니다.
- 기존 compose.production.yaml을 쓰던 서버의 볼륨을 새 compose.server.yaml이 자동으로 인계하지 않습니다. 별도의 검증된 전환 절차가 필요합니다.
- 배포 백업 파일은 서버 디스크에 남습니다. 별도 암호화 보관·오프사이트 전송·키 복구·보관 정책을 운영자가 설정해야 합니다.
