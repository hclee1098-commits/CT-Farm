### 기존 DB 적용 승인 전 준비 순서

1. Docker/네이티브 PostgreSQL을 사용할 수 있는 환경에서 원본에 쓰지 않는 별도 복원 DB를 새로 만듭니다.
2. 쓰기 중지 없이 일관된 원본 DB+파일 백업을 확보할 방법 또는 승인된 점검 구간을 먼저 결정합니다. 현재 지시는 서비스 중지를 허용하지 않으므로 임의 중지하지 않습니다.
3. 격리 복원본에 후보 SQL과 대응 Prisma 스키마를 적용하고 지문·파일 해시·인증 다운로드·타인 차단·락 경쟁·권한 회귀를 검증합니다.
4. API/UI 연결 결과, 원본 백업·별도 키 복구 증거, 적용 명령과 실패 시 되돌릴 소스 목록을 검토 가능한 형태로 준비합니다. 기존 열/데이터 삭제를 롤백 방법으로 쓰지 않습니다.
5. **기존 DB 적용은 별도 승인 대상으로 남습니다.** 현재는 복구 증거와 네이티브 검증이 부족해 적용 준비 완료도 아닙니다.

## 장애 알림과 디스크 감시

[상태 잠금](../../tools/monitoring/state-lock.mjs)을 사건 읽기-수정-저장·CLI 확인 처리에 적용했습니다. 동시에 잠금을 얻지 못하면 INCIDENT_BUSY로 실패하며 수집기는 다음 주기에 다시 시도합니다. 프로세스 비정상 종료 시 남은 lock은 임의 탈취하지 않습니다. 운영자가 PID 종료와 중복 실행 여부를 확인한 후 별도로 처리해야 합니다. 원격 전송 cursor까지 모든 다중 수집기 동작을 보호한 것은 아닙니다.

[발송 모듈](../../tools/monitoring/delivery.mjs)은 전환별 중복 키, 60초 발송 lease, 지수 재시도, 최대 5회 후 FAILED, 복구 전환, SMTP와 HTTPS 온콜 어댑터를 제공합니다. 기본 미설정이며 collector에서 외부 발송을 자동 활성화하지 않았습니다. 시험 대역 접수와 실제 SMTP 수신함 수신은 다릅니다. PROVIDER_ACCEPTED도 실제 수신 확인을 뜻하지 않습니다. 공급자가 멱등 키를 무시하거나 발송 후 프로세스가 종료되면 중복 전달 가능성이 남습니다. 큐는 300개 한도에서 명시적으로 실패하며 미전송을 몰래 버리지 않습니다. 장기 아카이브·관리자 UI·서버 권한/감사·원격 사건 동기화는 미완료입니다.

[발송 시험](../../tools/monitoring/delivery.test.mjs)은 실패·재시도·중복·복구·동시 lease, 보안 설정, 8개 독립 프로세스 갱신 보존을 검사했습니다. 실제 외부 메일/온콜 호출은 0회입니다. 지정된 시험 수신처와 자격 증명이 없으므로 외부 전송하지 않았습니다.

[디스크 검사](../../tools/monitoring/disks.mjs)를 collector에 연결했습니다. `MONITOR_DISK_DATABASE_PATH`, `MONITOR_DISK_UPLOADS_PATH`, `MONITOR_DISK_BACKUP_PATH`를 해당 수집기에서 실제 볼륨을 볼 수 있는 경로로 지정합니다. 미설정/경로 접근 실패는 unknown이고 원격 DB 볼륨을 추정하지 않습니다. 경로 원문은 이벤트에 남기지 않습니다. 기존 서비스 환경변수는 바꾸지 않았습니다.

## STAGING 후보와 검증 대기

[격리 Compose](../../deploy/round5/compose.local.yaml), [로컬 Caddy](../../deploy/round5/Caddyfile.local), [migration 이미지](../../deploy/round5/Dockerfile.migrate)를 작성했습니다. 별도 실행 ID·DB·Redis·업로드 볼륨·127.0.0.1:18443만 사용하며 기존 3000/4000을 참조하지 않습니다. 웹은 same-origin API, API는 STAGING·보안 쿠키 설정과 지정 CORS를 사용하도록 구성했습니다. 내부 CA TLS이며 공인 TLS가 아닙니다. Docker 엔진 부재로 Compose 해석·이미지 빌드·전체 기동은 **미검증**입니다.

기존 [웹 Dockerfile](../../deploy/Dockerfile.web)에 public 정적 파일 복사와 npm 다운로드 제한을 추가했습니다. public 복사가 없으면 standalone 배포에서 로고·문서센터가 누락될 수 있습니다. 이 수정의 Linux 이미지 빌드는 아직 미검증입니다.

다음 검증은 새 난수 시험 환경으로 `docker compose -f deploy/round5/compose.local.yaml config --quiet`부터 시작합니다. 기존 .env를 자동 재사용하지 않고 별도 `--env-file`을 지정해야 합니다. 환경값을 포함한 config 원문은 로그에 출력하지 않습니다. 기동 전에 새 프로젝트 ID·이미지·볼륨·포트만 사용함을 확인합니다. 볼륨을 삭제하는 종료 명령은 제공하지 않습니다.

기동 후 내부 CA를 시험 브라우저에만 신뢰 → 웹/API health → 합성 가입/로그인 → Secure/HttpOnly/SameSite 쿠키 → 허용/금지 CORS·Origin/CSRF 경로 → 합성 업로드/다운로드/타인 차단 → 같은 볼륨 재시작 → 이전 이미지 digest 롤백을 검증해야 합니다. 원본 DB에는 복원하지 않습니다. 공인 TLS 검증에는 시험 서버·도메인/DNS 권한·인증서 정책·배포 접근 권한·고정 이미지 digest와 별도 비밀 저장소가 필요합니다. 클라우드 배포·유료 자원 생성은 하지 않았습니다.

## 복구·부하 측정의 실제 범위

[합성 복구 시험](../../tools/round5/recovery.test.mjs)은 파일 2개 총 8MiB와 PGlite 스냅샷을 암호화하여 별도 키 경로에서 복구하고 DB 파일 메타데이터·해시·변조/오키 거부를 검사했습니다. heap 상한 512MiB, 실제 시험 프로세스 RSS 약 484MB, 복구 구간 약 491ms입니다. 이 수치는 API RSS·네이티브 pg_restore·운영 RTO/RPO·오프사이트 복구가 아닙니다. 같은 PC에 분리한 임시 경로이며 진짜 별도 보관소 검증이 남습니다. 원시 측정값은 recovery.log에 있습니다.

PGlite 농장 시험에 대시보드 20요청/동시 4개 측정이 포함되며 실행별 performance-pglite.json으로 보존합니다. 로그인·사진·센서 부하와 API 프로세스 메모리·DB pool은 미검증입니다. 기존 4차 성능 JSON을 더 이상 덮어쓰지 않도록 수정했습니다.
