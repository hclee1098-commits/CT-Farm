# SECURE STARTER V6 공통 기반의 실제 검증 상태

기준일: 2026-10-29, 한국 시간. **개발환경의 검증 범위는 통과했지만 실제 운영환경 완성으로 판정하지 않습니다.** 시험 자료는 격리 DB·시험용 Redis에만 만들었습니다. 기존 CT-Farm 사용자 DB를 초기화하지 않았습니다.

## 안전한 실행 명령

프로젝트 폴더의 Windows PowerShell 5.1에서 실행합니다. 기존 STARTER는 START의 호환 이름으로 유지합니다.

```powershell
Set-Location C:\workspace\CT-Farm
.\SECURE-LIFECYCLE.ps1 -Action STATUS
.\SECURE-LIFECYCLE.ps1 -Action START
.\SECURE-LIFECYCLE.ps1 -Action DIAGNOSE
.\SECURE-LIFECYCLE.ps1 -Action RESTART
.\SECURE-LIFECYCLE.ps1 -Action STOP
```

START는 해당 프로젝트의 DB·Redis와 API·웹·수집기를 실행합니다. 정상 실행 기록과 포트 소유권이 맞으면 같은 PID를 유지합니다. STOP/RESTART는 실행 기록의 프로젝트·절대 경로·PID 생성 시각·실행 경로·포트 소유권을 확인합니다. 수동 실행/다른 프로세스가 포트를 차지하면 **DB를 멈추기 전에 거부**합니다. 수동 프로세스를 런처가 자동으로 인수하거나 이름만 보고 종료하지 않습니다. 이 경우 그 프로세스를 실행한 터미널에서 직접 종료한 뒤 START를 사용합니다.

STATUS는 포트·readiness·소유권·해당 Docker 상태를 조회합니다. DIAGNOSE는 관련 로그 파일 위치와 허용된 숫자 상태 필드만 보여 줍니다. 예외·자유 텍스트·환경값 원문은 비밀정보 보호를 위해 생략합니다. STATUS 성공 종료 코드 자체는 모든 서비스가 정상이라는 뜻이 아니므로 표시 내용을 확인합니다. 진단을 위해 DB reset·볼륨 삭제·환경파일 재생성을 하지 않습니다.

## 발견하여 수정한 오류

1. 실행 명령 부족: START 별칭·STATUS·RESTART·DIAGNOSE를 기존 안전 런처에 추가했습니다.
2. 수동 서버가 있는데 STOP이 DB만 멈출 수 있는 경계: 포트·실행 기록 소유권 사전 검사를 추가했습니다. 실패 시 변경 전에 중단합니다. 다른 프로젝트와 같은 구형 cmd/npm 문자열만으로 소유권을 인정하던 경로는 거부하도록 수정했습니다. 구형 기록은 수동으로 해당 터미널에서 종료한 후 START로 새 실행 기록을 생성합니다.
3. Windows의 플랫폼/메일 통합 시험이 REDIS_SERVER_BIN을 요구해 실행 불가: Docker에 이미 있는 redis:7-alpine을 loopback 임시 포트와 tmpfs로 사용합니다. 새 시험 컨테이너만 고유 ID로 정리하며 영구·익명 볼륨은 생성/삭제하지 않습니다. 이미지 자동 다운로드도 하지 않습니다. 네이티브 실행 파일 지정 경로는 유지합니다.
4. 플랫폼 통합이 성공 메시지 후 종료되지 않는 오류: SIGTERM으로 종료된 자식은 exitCode=null·signalCode 값이 남는 것을 처리하지 못했습니다. signalCode를 함께 검사하여 이미 끝난 자식의 exit 이벤트를 다시 기다리지 않도록 수정하고 정상 종료까지 재검증했습니다.

## 이번 시험 결과

- API 157/157, 웹 18/18, 네이티브 PostgreSQL 격리 농장 통합 27그룹 통과.
- 플랫폼 통합 29건: 실제 Prisma/HTTP·격리 PGlite PostgreSQL·실제 Redis. 계정 메일 통합 8건: MemoryMailTransport·실제 DB/HTTP, 외부 메일 전송 아님.
- 로컬 TCP SMTP 수신 시험 통과. 외부 SMTP 계정·받은편지함은 검증하지 않았습니다.
- SQL 보존 8건, 암호화 백업 단위 7건, 모니터링 6건, 배포 제어 4건, 포털 7건 통과.
- Windows PowerShell **5.1** 파서·PS1 **6개 BOM** 및 런처 안전 경계 9건 통과. START 중복 PID 유지, RESTART·STOP·최종 START와 수집기 heartbeat를 실제 확인했습니다.
- API·웹 배포 빌드 및 전체 npm audit 알려진 취약점 0건. audit는 검사 시점의 알려진 의존성 취약점이며 전체 보안 보증이 아닙니다.

실행 결과와 마지막 서버 상태는 [개발현황](../CT-Farm-개발현황.md), 프로젝트 `verification/ct-farm-foundation-results.json`에 기록합니다. 테스트 성공 출력만 보고 프로세스가 실제 종료되기 전에 완료 처리하지 않습니다.

## 백업·복구와 운영 준비 순서

변경 전 소스: backup/ct-farm-foundation-before-20261029-211418.zip. DB 백업: backup/ct-farm-postgres-1793276139554.ssbk. 별도 복원 DB: ct_farm_verify_d57652a9d7e2. 원본에 마이그레이션 적용·시험 fixture 주입·DB reset·볼륨 삭제를 하지 않았습니다. 복호화 키 값은 문서에 기록하지 않습니다.

소스 복구는 ZIP을 별도 폴더에 풀어 필요한 변경만 비교 복원합니다. DB는 원본을 덮어쓰지 말고 별도 DB에 복원해 무결성·마이그레이션·권한·파일 정합성을 확인한 후 운영 담당자와 전환합니다. 자세한 절차는 [배포·백업 복구](../05-운영과보안/배포와-백업복구.md)를 따릅니다.

다음 우선순위는 (1) 업로드 포함 오프사이트 복원 훈련과 RTO/RPO → (2) 실제 Linux STAGING·공인 HTTPS·원격 모니터링 → (3) 외부 메일·온콜 알림과 비밀 회전 → (4) 부하·접근성·장기 보존 검증입니다. 실결제·장치 원격 제어는 이번 공통 기반 검증으로 활성화되지 않습니다.
